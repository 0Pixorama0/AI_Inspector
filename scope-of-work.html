Purpose & structure

Introduction

This document is the definitive statement of what Pixorama will deliver, how each deliverable will be accepted, and the terms under which the work proceeds.

Where this Statement of Work and the platform proposal differ, this document prevails on matters of scope, acceptance, schedule and commercials. Anything not expressly listed as in scope in Section 05 or 06 is out of scope and is handled through the change-control process in Section 14.

02
Terms

Definitions

Capitalised terms used throughout this document carry the meanings below.

Platform
The AI Device Inspector software system described in Sections 04–06, in all its surfaces (station kiosk, back-office application, client portal) and services.
Deliverable
A discrete, identified output listed in Section 05 or 06, each with its own acceptance basis.
Edge Node
The on-site hardware and software that owns the cameras and runs inference at a facility.
Detection
A single defect identified by the model on a captured image, with class, confidence, severity and region.
Grade Profile
A configurable, versioned rule set that converts a confirmed defect set into a commercial grade for a given buyer.
Holdout Set
A frozen, labelled sample of images used once to measure model accuracy and never used for training.
UAT
User Acceptance Testing — structured testing performed by the Client's own operators and supervisors against agreed scripts.
Go-Live
The point at which the Platform is used to process live production stock on at least one line.
Business Day
Monday to Friday excluding public holidays in the Client's jurisdiction.

Why

Project objectives

The Platform is accepted as meeting its purpose when it delivers against these objectives, evidenced by the acceptance criteria in Sections 12–13.

Consistent gradingOne model and one rule set applied to every device, independent of operator or shift.
SpeedCapture-to-grade in under 60 seconds per device on the target hardware.
DefensibilityEvery grade backed by photographs, a defect map and a complete audit trail.
Measurable accuracyDetection performance proven against a frozen holdout set to an agreed threshold.
Operational visibilityThroughput, yield and defect trends visible to supervisors and administrators.
IntegrationRecords flow to the Client's existing systems without manual re-keying.

06
Build & hand-over

Technical deliverables

Beyond the functional modules, the engagement delivers the following engineering and documentation assets.

Front end
  • Next.js 16 / React 19 / TypeScript application serving station, back-office and client-portal surfaces
  • Tokenised design system on Tailwind v4; dark-first station UI
  • Virtualised data grids (100k+ rows), real-time station status (WebSocket + SSE fallback)
  • Offline-tolerant capture (service worker + IndexedDB)
  • WCAG 2.2 AA on operator and supervisor journeys; LCP < 2.0s, INP < 200ms budgets
Back end
  • NestJS / TypeScript API with OpenAPI specification
  • PostgreSQL 16 with row-level security; Redis + BullMQ job queue
  • S3-compatible object storage with presigned uploads
  • Python FastAPI inference service; TensorRT model serving on the Edge Node
  • Transactional-outbox webhooks; headless-Chromium PDF reporting
Infrastructure & operations
  • Dockerised services; Terraform-defined environments (staging + production)
  • GitHub Actions CI/CD with SCA, SAST and secret scanning
  • OpenTelemetry tracing to Grafana; Sentry error tracking
  • Cloud control plane plus one on-site Edge Node configuration
  • Nightly point-in-time backups with a 30-day recovery window
Documentation & enablement
  • Architecture overview and data-model reference
  • API reference (OpenAPI) and integration/webhook guide
  • Administrator, supervisor and operator user guides
  • Model retraining and evaluation guide
  • Operational runbooks and recorded training walkthroughs

Sign-off

Acceptance process & criteria

How each deliverable and milestone is reviewed, corrected and accepted.

Review window

On submission of a deliverable, the Client has five Business Days to review it against its acceptance basis (Section 05) and either accept it or issue a written list of defects referencing specific criteria.

Correction

Pixorama corrects valid defects and re-submits. The review window restarts for the re-submitted deliverable, limited to the previously raised items.

Deemed acceptance

A deliverable is deemed accepted if the Client raises no written defects within the review window, or if it is used in production.

Partial acceptance

A deliverable is not rejected as a whole for minor (S3/S4) defects; it is accepted with those items logged for correction inside the warranty period.

Milestone gates

Gate milestones (M4–M6) require the associated deliverables to be accepted and the relevant tests in Section 13 to have passed.

Defect severity & correction targets

S1 · Critical

Blocks core use

Capture, grading or data integrity is unusable, with no workaround.

Fix: same Business Day
S2 · Major

Serious impairment

A key function fails or a workaround is costly.

Fix: 2 Business Days
S3 · Minor

Limited impact

A non-critical issue with an easy workaround.

Fix: next release
S4 · Cosmetic

Trivial

Visual or textual polish; no functional impact.

Fix: as scheduled
13
Four-week test phase

Testing & quality assurance

Testing is a resourced, gated phase — not a hope. Each gate below must pass before the associated milestone is accepted.

W9

System & regression

Full SIT across station, API, inference and integrations; automated regression on a frozen build.

W10

UAT & accuracy

Client-run UAT scripts on real stock; model scored on the frozen holdout set.

W11

Perf · security · a11y

Load and soak tests; third-party penetration test; WCAG 2.2 AA audit; failure drills.

W12

Pilot

One live line, monitored, with the prior process running alongside.

Acceptance gates

Quantified thresholds
  • Detection recall ≥ 0.90 and precision ≥ 0.85 on the top ten defect classes, measured on the holdout set
  • API p95 < 300 ms at 3× expected peak throughput
  • Zero open S1/S2 defects; regression suite green on three consecutive runs
  • No critical or high security findings open
  • WCAG 2.2 AA audit passed on operator and supervisor journeys
Evidence provided
  • Per-class model scorecard against the holdout set
  • Grade-agreement study — platform grade vs expert human grade
  • Load and soak test reports
  • Penetration test report and remediation log
  • UAT results with a fix-or-defer decision on every item
14
Managing scope

Change control

The deliverables in Sections 05–06 are the agreed scope. Any change to them follows this process; nothing outside it alters price or timeline.

Raising a change

Either party may raise a change request in writing, describing the change and its reason.

Impact assessment

Pixorama assesses the impact on scope, timeline and price and issues a change note, normally within three Business Days.

Approval

Work on a change begins only once the Client approves the change note in writing. Approved changes are appended to this Statement of Work.

Swaps

By agreement, a new item of equivalent size may be exchanged for an unstarted deliverable at no change to price or timeline.

Standing changes

Rules, taxonomy, grade profiles and branding are configurable and are changed by the Client without a release — these are not change requests.

After go-live

Warranty, support & IP

Hypercare

Thirty days of close monitoring and priority defect response from Go-Live, at no additional cost.

Warranty period

Ninety days from Go-Live during which S1 and S2 defects in delivered scope are corrected at no cost.

Exclusions

Warranty excludes issues caused by Client changes to configuration, unsupported environments, or third-party systems outside the delivered scope.

Ongoing support

Support or a managed-service arrangement beyond warranty is available under a separate agreement.

Ownership

On full payment, intellectual property in the bespoke deliverables and the trained model weights transfers to the Client.

Pre-existing IP

Pixorama retains its pre-existing tools, libraries and know-how, and grants the Client a licence to use them as embedded in the deliverables.

Third-party components

Open-source and third-party components remain under their own licences, disclosed on handover.

Confidentiality & data

Each party protects the other's confidential information; personal data is handled per the parties' data-processing terms.

Precedence

This Statement of Work governs scope, acceptance, schedule and commercials for this engagement. Legal terms (liability, warranties, IP, data protection, termination) are governed by the parties' master services agreement; where that agreement is silent, the clauses above apply. Nothing here is legal advice, and the parties should have this document reviewed before signature.
